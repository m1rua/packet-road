# Что именно измеряется

## Точка наблюдения

`ip route get <selected_ip>` спрашивает ядро Linux, какой интерфейс, source address и next hop оно выберет для цели. Это не обязательно публичный IP: за NAT процесс видит локальный исходящий адрес. При policy routing для конкретного сокета, нескольких таблицах и сетевых правилах результат может отличаться. Нельзя выводить существование SNAT только из частного адреса.

MAC берётся из `ip neigh` только для непосредственно подключённого gateway. Запись может отсутствовать, устареть или не использоваться для point-to-point интерфейса. В IPv6 это neighbor discovery, а не ARP. Активный ARP-запрос не отправляется; MAC чужих маршрутизаторов через Интернет недоступен.

Старый код выбирал маршрут к 8.8.8.8 вне зависимости от цели; новый запрашивает маршрут к выбранному IP. В Docker это обычно bridge и gateway контейнера, в k3s — сеть pod/CNI. Сервер не видит локальный gateway посетителя браузера.

## DNS

Используется resolver окружения через dnspython с A и AAAA запросами, timeout 1 s и lifetime 2 s на тип. Ответы CNAME обрабатывает resolver. Если один тип недоступен, сохраняются адреса второго. DNS-этап возвращает адреса, а не полный путь рекурсии от root. Старый скрипт отправлял запрос root-серверу, но referral без рекурсивного обхода не равен разрешению домена.

Перед сетевыми этапами проверяются **все** возвращённые адреса: любой non-global, multicast или IPv4-mapped IPv6 запрещает API-диагностику. Затем выбранный IP передаётся напрямую в `socket.connect`; имя используется только для SNI, проверки сертификата и HTTP Host. Повторного DNS в соединениях нет. Это уменьшает риск DNS rebinding. HTTPS redirects не выполняются. URL, path, userinfo, zone ID и порт внутри строки цели не принимаются.

CLI позволяет `--allow-private` для собственной лаборатории; API такой опции не предоставляет. Список разрешённых API-целей обязателен независимо от публичности IP. DNS-запрос для разрешённого имени всё равно является сетевой операцией к настроенному resolver.

## Traceroute и права

Scapy-версия вручную посылала TCP SYN с TTL 1..30 и показывала ICMP Time Exceeded либо ответ TCP. Это полезно для изучения заголовков и фильтрации, но требует raw sockets. Простое требование UID 0 давало слишком широкие полномочия.

Новая версия использует системный Linux `traceroute` в обычном UDP-режиме: одна проба на TTL, до 20 hops, ожидание 0.3 s, общий subprocess timeout 8 s. Обычные UDP sockets и Linux error queue позволяют запускать его без `NET_RAW`, `NET_ADMIN`, root и privileged. Сохранены TTL, наблюдаемые адреса, RTT и таймауты. Потеряны ручное конструирование TCP SYN, фиксированный TCP source port и интерпретация SYN/ACK/RST в traceroute. Доступность TCP порта измеряется отдельным `connect`, а не traceroute.

UDP и TCP могут идти разными путями из-за ECMP, политик и фильтров. `*` означает отсутствие ответа в срок, а не обязательно сломанный router. ICMP может фильтроваться или ограничиваться. `reached` означает ответ с адреса назначения, не доказательство успешного HTTP. Если процесс traceroute не уложился в общий timeout, этап возвращает ошибку; промежуточный вывод завершившегося по timeout процесса сейчас не сохраняется.

## TCP, TLS, HTTP

TCP — отдельное соединение с временем connect. TLS — отдельное соединение с системной проверкой цепочки и имени/IP сертификата, SNI для домена; выводятся протокол, cipher, subject, issuer, SAN, срок действия из `getpeercert`. Ошибка проверки не обходится через insecure fallback.

HTTP использует ещё одно соединение к тому же IP: plaintext для порта 80, HTTPS для остальных CLI-портов. Выполняется `HEAD /`, HTTP/1.1, без загрузки тела и без redirects. Тайминги HTTP относятся именно к этому соединению: connect+TLS, первый байт после установления соединения, завершение заголовков. У TLS-этапа собственный тайминг; их нельзя суммировать как этапы одного HTTP-запроса. Размер заголовков ограничен 16 KiB и абсолютным сроком 2 s после отправки. Общие connect и TLS handshake имеют timeout по 2 s. HTTP-ошибка сохраняет уже полученный независимый TLS-результат. Код HTTP 4xx/5xx — успешное измерение статуса, не ошибка механизма диагностики.

## Граница безопасности

Bearer token сравнивается constant-time. Запуск API без токена длиной 32+ запрещён. Не включайте debug и не передавайте токен в URL. Логи не содержат токен и payload запросов. API — синхронные bounded операции в thread pool: максимум 2 одновременно и 10 запусков за 60 секунд **на один процесс**. Разрешён только один worker. Несколько pod умножат лимит; общего распределённого rate limiter нет. Утилиты запускаются списком аргументов, без shell, с фиксированным PATH и timeout.

Метрики не имеют label по домену/IP/token: так не растёт cardinality и не раскрываются цели через метрики. `/metrics` без токена предназначен для доверенной сети, ограниченной Kubernetes NetworkPolicy; health также открыт. Доступ к API требует TLS на внешнем reverse proxy или закрытой сети/port-forward. Compose слушает только loopback. Публичный ingress намеренно не настроен.

Проверка `is_global` не заменяет сетевой firewall: нестандартные маршруты публичных IP к внутренним сервисам, NAT64 и компрометация маршрутизации требуют изоляции на уровне сети. Приложению нужен egress для реальных измерений; универсальная egress NetworkPolicy здесь не предлагается. На реальном стенде ограничьте egress допустимыми сетями и resolver с учётом адресов целей. Не используйте shared API для недоверенных пользователей без отдельной модели доступа, ingress-лимитов и пересмотра ресурсов.
